# APIEase Liquid request semantics

A result alias exists only after its call tag executes. Contract examples such as `result.data.orders` do not supply a `result` variable, and a declared dependency does not invoke the dependency. A coordinator that owns source retrieval must call its reader first, check its response, then iterate that actual alias. Do not assume reader output is supplied by a prior request unless the assignment explicitly defines that runtime input.

Use `pathParamsEmbedded` for address substitutions and `queryParamsEmbedded` for query parameters. Address placeholders have the form `{sourceBaseUrl}` or `{page}`, without a dollar sign or angle brackets. Define whether a base URL includes its scheme and append the documented path exactly once. `bodyEmbedded.variables` cannot substitute an address or set headers. Liquid-request configuration arrives through `liquidParamsEmbedded` and can fill `{parameterName}` placeholders, including names not saved on the request. Keep saved Liquid parameters for defaults or server-side configuration and validate required values before any call. Keep secure source credentials on the source HTTP helper; never send a `preserve` object as a runtime header. Use the separate `{% function {"functionId":"saved-function-handle","args":{...}} as mapped %}` tag to invoke a function, and read its rendered JSON output directly from the alias; never call it with `requestId`.

Use Liquid's `json` filter for interpolated strings, objects, booleans, numbers, and arrays. Insert its result without surrounding quotes. This preserves quotes, backslashes, newlines, nulls, and JSON types. Do not interpolate raw user strings into JSON, double-encode `bodyEmbedded`, or use unsupported `parse_json` filters. A captured JSON string must be supplied in a position that parses it as JSON, not filtered again into a string. The examples below illustrate serialization and binding only; they do not verify a live Shopify schema or execute during design.

Liquid output expressions and assignments do not support JavaScript object or array literals. Render static JSON as template text with individually interpolated values, never `{{ {"status":"completed"} | json }}`. Comparisons and `contains` belong in `if`, `unless` or `while` conditions; to store their result, initialize a boolean and assign it inside that condition. Do not write `assign valid = response.status >= 200` or `assign repeated = cursors contains cursor`. Balance each `if`, `unless`, `for` and `while` with its own closing tag; a standalone `call` opens no block. When correcting syntax, retain the complete workflow, loops, and guards; removing required behavior does not repair the resource.

The runtime uses strict variables and filters. A missing property throws even before `default` runs. For optional fields, use APIEase's `map` filter, which accepts an object and safely reads a property, followed by `first` and `default`, as shown below. Check HTTP status before consuming success data. For GraphQL, check top-level `errors` as well as operation `userErrors`; a mutation is successful only when it has no errors and returns the required result identifier. Report failures and skipped work distinctly from completed work. Do not emit an unconditional success result after an attempted call. Preserve all specified quantities, notes, and identifier tags. When exact unique matching is required, count exact matches to the requested value instead of trusting search relevance or taking the first node. Use the provider's documented search field (for example `tag:` for Shopify order tags), with the external identifier tag as its value.

GraphQL commonly omits `errors` on success and can omit `data` or return a null mutation result on failure. An `if` condition still evaluates a missing property: `{% if response.data.errors and response.data.errors.size > 0 %}` throws on an ordinary successful response. Safely extract the optional field first (`{% assign errorCount = response.data | map: 'errors' | first | default: '' | size %}`), then test `errorCount > 0`. Apply the same safe extraction at every nullable segment when reading operation results, `userErrors`, and result IDs; a later comparison with `blank` cannot rescue a direct read that already threw. Audit every helper response, including duplicate checks, against both its success and failure shape before returning the source.

An assignment ending in `map` and `first` can itself produce an undefined variable. Testing that assigned name with `if`, `blank`, or `nil` still throws. Finish optional extraction with a defined fallback, or guard the read with `has_key`. APIEase's `has_key: 'field'` checks an object's own top-level field and preserves presence for `''`, `0`, `false`, and null. Assign its boolean result before a condition, then read the field only inside the true branch. It does not search nested objects or interpret dotted keys as paths. `where` without a comparison uses JavaScript truthiness, so it must not be used as a general field-presence check.

After guarding presence, use `is_type` to check the original value without coercion. Supported types are `string`, `integer`, `number` (finite), `boolean`, `array`, `object` (non-null and not an array), and `null`. Assign each filter result before a conditional; do not put filters inside `if` expressions. An empty string is a string, zero and negative integers are integers, false is a boolean, and an empty array is an array. Validate required collections as arrays before iteration, preserving empty arrays as successful zero results. Apply this to reader rows, candidate nodes and required mutation `userErrors`. Guard each nullable parent before reading its child. Optional top-level GraphQL `errors` may be absent on success; a required collection may not.

Keep presence, type and business restrictions separate. Enforce nonempty strings, positive quantities, ranges, formats or other value restrictions only when the assignment's agreement requires them. Do not strengthen a `String` contract into a nonempty string or an `integer` contract into a positive integer. Preserve the same permitted values when validating source rows, helper candidates and corrected source. Do not trim, coerce or round input to change its eligibility; downstream helper failures still follow the agreed failure policy.

Keep validation blocks shallow. Carry one validity/failure flag through successive guarded steps, closing each block before the next step. A `has_key` check already rejects null, arrays and scalar parents, so it does not need an additional object-type branch. Avoid a separate deeply nested `else` and repeated failure-detail assignments for every response property. Record the failed stage once at its common exit, while retaining every required status, error, shape, pagination and value check. Inspect the block stack at source-part boundaries; indentation does not close a Liquid block. Apply this structure during the single correction as well as initial construction.

For paginated results, distinguish the two boolean values explicitly: `pageInfo | where: 'hasNextPage', true | size` and `pageInfo | where: 'hasNextPage', false | size` establish a valid true or false flag. A truthiness-only presence check rejects the normal final page. Continue through all necessary pages, require a nonempty next cursor when true, and fail if a cursor repeats or traversal cannot complete. Do not report absence or uniqueness after an unreadable or incomplete page sequence.

APIEase supports `{% while condition %}...{% endwhile %}` for cursor traversal. Initialize a defined `hasMore = true` and cursor `nil`; use `while hasMore and rowFailed == false`, updating both from the checked response on every iteration. The first cursor encoded with `json` is JSON `null`. Set `hasMore = false` for a validated terminal page or an agreed failure. When the agreement requires every page or the complete candidate set, keep traversing even after finding a duplicate or multiple exact SKU matches: record that outcome provisionally, continue with the returned cursor, and finalize the row only after a valid terminal page. An early match followed by an unreadable later page still follows the agreed failure policy. Do not infer permission to stop from the fact that existence is already known; an early positive-match exit requires an explicitly agreed policy compatible with the fixed traversal criterion. Audit a first page with a match and hasNextPage:true followed by both a successful and a failed next page. Do not invent a fixed page-count cutoff such as `for page in (1..1000)`. Runtime call-response, cumulative response, and conditional-iteration budgets still fail execution if exhausted; such an exception is never proof of absence or uniqueness. Require cursor progress independently of those budgets.

For JSON-producing workflows, use whitespace-control delimiters (`{%- ... -%}`) on control tags so indentation does not accumulate on every row or page. Preserve literal payload values and captured JSON content; trim template layout whitespace, not source data. The runtime's output-byte limit also counts whitespace.

Search-language escaping is separate from JSON serialization. For a Shopify `tag:` or `sku:` filter, quote the complete search value and escape its backslashes and double quotes for that search language first, then apply `json` to the finished search expression when binding GraphQL variables. The JSON filter alone does not preserve a quoted search literal. Match returned SKUs and tags exactly against the original unescaped values.

For literal search escaping, define the backslash with `{% assign backslash = '%5C' | url_decode %}` and the quote with `{% assign quote = '%22' | url_decode %}`. These standard filters produce exactly one character without a backslash literal crossing the provider JSON encoding boundary. Build replacements using `append` and apply backslash replacement before quote replacement. Do not replace these definitions with captured or quoted backslash literals.

An unreadable initial row collection can return the agreed whole-workflow error. A malformed row within a readable collection is a per-row failure, unless the contract explicitly says otherwise. For a row-processing loop, record the row's outcome before every `continue`, `break`, or other exit. A failure guard must append a failure detail identifying the source row (use its position when the source identifier is missing), processing stage, and reason, and increment the failure count before advancing. Setting `rowFailed` and then continuing is insufficient: it bypasses a common recording block at the bottom of the loop. Either record inside each early guard or reach one common finalization block without bypassing it. Missing required source fields, failed calls, and unreadable required helper results are failures, including duplicate checks; they prevent all dependent writes. Verify each mutation's required returned payload and identifiers as well as HTTP status, GraphQL errors and operation userErrors before advancing or counting success.

Keep ambiguous matches and other skips separately accounted for, without counting them as completed rows. Empty result arrays are successful searches with zero matches, not transport failures. Liquid's `default` replaces empty arrays too, so do not interpret a defaulted empty array as a failed search. After checking status and errors, iterate the candidate array and count exact matches; zero or multiple exact matches follow the assignment's create or skip policy. Reconcile completed, failed, ambiguous and other skipped rows against every reader row exactly once. An overall complete result requires all required work to be completed, with no failed, ambiguous, skipped or unaccounted rows. Audit these exits and the final completion predicate again during correction; a later successful row must not erase an earlier failure.

Initialize the row's mutation branch before any guard, including failed and
ambiguous rows. Classify an ambiguous match before testing create/update guards;
an assignment placed later cannot prevent an earlier undefined or stale read.
Trace both an ambiguous first row and an ambiguous row after a successful update.
Neither may execute a mutation from the prior row's branch.
